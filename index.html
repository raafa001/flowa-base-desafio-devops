bitbucket-pipelines.yml · app-dotnet-service

Pipeline da aplicação: qualidade antes de qualquer deploy

Cada merge passa por uma bateria obrigatória: formatação + testes com cobertura, SAST (DevSkim), SCA (Trivy filesystem/imagem), DAST (OWASP ZAP) e só então a imagem é enviada ao ECR com tags imutáveis.

  • • Build/Test: dotnet format impede drift e dotnet test gera LCOV para auditoria.
  • • SAST + SCA + DAST: DevSkim, Trivy (fs+image) e ZAP baseline bloqueiam HIGH/CRITICAL antes do deploy.
  • • Push ECR com OIDC: step `build_push_ecr` assume a role temporária e versiona a imagem via digest.
  • • Deploy DEV → STG: scripts `deploy-ecs.sh` e `deploy-ec2.sh` reaproveitam a mesma imagem; STG só acontece após sucesso em DEV.
  • • Promoção e rollback: tags `-staging` e pipelines `deploy-manual`/`rollback` permitem reversão apontando apenas a tag/digest.

O pipeline ainda exporta relatórios (coverage, DevSkim, Trivy, ZAP), garante execução em runners self-hosted e usa apenas secrets do AWS Secrets Manager.

bitbucket-pipelines.yml CI/CD .NET 
- step: "CI: Build Imagem e Push para ECR"
    oidc: true
    script:
      - eval "$(./scripts/oidc-assume-role.sh ...)"
      - docker build -t ${ECR}/${REPO}:${IMAGE_TAG} .
      - docker push ${ECR}/${REPO}:${IMAGE_TAG}

- step: "CD: Deploy em DEV"
    trigger: manual
    script:
      - ./scripts/deploy-ec2.sh --env dev --tag ${IMAGE_TAG}
      - ./scripts/deploy-ecs.sh --env dev --tag ${IMAGE_TAG}
      - aws ecr put-image ... --image-tag "${BASE}-staging"

bitbucket-pipelines.yml · infra-terraform

Pipeline da infraestrutura: guard rails antes do apply

  • • Fmt + Validate: instala Terraform 1.7.4, fixa timezone e ativa o plugin cache para execuções mais rápidas.
  • • Checkov obrigatório: `Security: Checkov IaC Scan` falha em qualquer severidade alta.
  • • Auto plan DEV: gera `tf-artifacts/dev.tfplan` e só libera o apply após aprovação manual.
  • • Custom runner: `terraform-runner` aceita ações `plan/apply/destroy/import` e alvo por módulo (`module.ecs`, `module.waf`...).
  • • Drift diário: dois cron jobs (09h e 17h) comparam `dev` e `staging`, enviando alerta se o exit-code for 2.

Todo acesso AWS usa OIDC (script `scripts/oidc-assume-role.sh`), eliminando chaves fixas e permitindo auditoria por session name.

bitbucket-pipelines.yml Terraform 
default:
  - parallel: [*tf_fmt_validate, *checkov_scan]
  - step: *tf_auto_plan_dev
  - step: *tf_manual_apply_dev

custom: terraform-runner
  variables:
    ACTION: [plan|apply|destroy|import]
    TARGET_RESOURCE: module.ecs | module.alb | ...
  steps:
    - step: *tf_fmt_validate
    - step: *checkov_scan
    - step: "Executar Ação Selecionada"

Dockerfile · app-dotnet-service

Imagem enxuta, segura e autosuficiente

  • • Build multi-stage: restaura, testa e publica no estágio sdk; runtime usa apenas o `aspnet`.
  • • Hardening: atualiza o Debian, remove cache e roda como usuário `appuser` (não-root).
  • • Porta 5000: `ASPNETCORE_URLS=http://+:5000` garante compatibilidade com ECS e EC2.
  • • Healthcheck nativo: consulta `/api/status` a cada 30s e ativa rollback automático no CodeDeploy.
  • • Testes dentro da imagem: `dotnet test ... --results-directory` garante que nenhuma regressão escape.

Tudo isso respeita a exigência do desafio de expor `/api/status` respondendo “Healthy”.

Dockerfile Container 
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
RUN dotnet test ATG_TESTE_API.csproj --logger trx
RUN dotnet publish ... -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
RUN apt-get update && apt-get upgrade -y
USER appuser
ENV ASPNETCORE_URLS=http://+:5000
HEALTHCHECK CMD curl -f http://localhost:5000/api/status || exit 1
ENTRYPOINT ["dotnet", "ATG_TESTE_API.dll"]

infra-terraform/modules

Onde está cada manifesto Terraform

O repositório se comporta como LEGO: ambientes em environments/ apontam para módulos reutilizáveis.

  • • networking: cria VPC com sub-redes privadas/públicas, NAT, Flow Logs e tags para FinOps.
  • • alb + waf: ALB público recebe tráfego e associa o AWS WAF com regras OWASP Top 10.
  • • ecs / ecr / iam: stack completa para Fargate (autoscaling, roles, secrets, log groups).
  • • ec2: instancia privada com target group, user data renderizando systemd, criação dos usuários `deploy` e `app-runner` e patching via SSM.
  • • lambda_scheduler: funções que ligam/desligam ECS e EC2 às 09h/18h.
  • • cloudwatch: dashboards “golden” e alarms (latência, 5xx, CPU, memória, rede, contagem de instâncias).
  • • secrets: Secrets Manager + KMS dedicado por ambiente para app e DB.

Para operar: entre em environments/dev ou staging, ajuste o terraform.tfvars e use o pipeline custom `terraform-runner`.

deploy-ec2.sh + systemd + cron

Execução tradicional em Linux (EC2)

  • • Pipeline: `deploy-ec2.sh` faz `dotnet publish`, zipa, envia ao S3 (`ARTIFACT_BUCKET`) e executa um documento SSM para atualizar o servidor.
  • • User data: `modules/ec2/templates/user_data.sh.tpl` cria os usuários deploy_user e app_user, instala .NET 8, systemd e cron 09h/18h.
  • • Systemd: `systemd/flowa-base-teste-devops.service` roda como `app-runner`, escuta na porta 5000 e reinicia em caso de falha.
  • • Cron/healthcheck: `cron/healthcheck.sh` chama `/api/status` a cada 5 min e reinicia o serviço se necessário.
  • • Lambda EC2: `module.lambda_scheduler` também envia `StartInstances`/`StopInstances` para manter o servidor desligado fora do horário útil.

Assim atendemos a exigência de executar a mesma aplicação como container e como processo tradicional.

systemd/flowa-base-teste-devops.service EC2 
[Service]
User=app-runner
WorkingDirectory=/opt/flowa/base/current
EnvironmentFile=/etc/flowa-base.env
ExecStart=/usr/bin/dotnet /opt/flowa/base/current/ATG_TESTE_API.dll
Restart=on-failure
RestartSec=5

# Cron gerado no user_data
0 9 * * 1-5 systemctl start flowa-base
0 18 * * 1-5 systemctl stop flowa-base
